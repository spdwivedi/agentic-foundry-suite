# Architectural Evaluation: Redis Cluster vs. KeyDB for High-Throughput Caching

**To:** Engineering Leadership  
**From:** Principal Database Infrastructure Architect  
**Subject:** Infrastructure Evaluation: In-Memory Caching Layer (100k RPS)

---

### 1. Executive Summary & Final Recommendation
For a deployment prioritizing **low-memory overhead** while maintaining a sustained 100k read req/sec, **KeyDB is the recommended solution.**

KeyDB’s multi-threaded architecture allows it to achieve higher throughput (104.2k QPS) using a single instance compared to a 6-node Redis Cluster (98.9k QPS). Crucially, KeyDB demonstrates a **21.6% reduction in resident memory (RSS)** and a **25.8% reduction in per-key memory overhead**. By consolidating the workload into a single instance, we eliminate the cluster-wide metadata overhead and inter-node communication latency, resulting in a more efficient, lower-footprint deployment.

---

### 2. Threading Model & Architectural Comparison
*   **Redis Cluster (Single-Threaded Shard Model):** Redis utilizes a single-threaded event loop per shard. To handle 100k RPS, the architecture necessitates horizontal scaling (sharding). This introduces "cluster tax"—the overhead of maintaining hash slots, inter-node gossip protocols, and connection management across multiple processes.
*   **KeyDB (Multi-Threaded Shared-Nothing Model):** KeyDB utilizes a multi-threaded architecture that assigns specific threads to handle I/O and command execution. It employs a shared-nothing approach where each thread manages its own event loop, effectively utilizing modern multi-core CPUs without the contention issues typically associated with global locks. This allows a single KeyDB instance to outperform a multi-node Redis cluster.

---

### 3. Throughput & Latency Analysis at 100k RPS
| Metric | Redis Cluster (6 Nodes) | KeyDB (1 Instance) | Delta |
| :--- | :--- | :--- | :--- |
| **Measured QPS** | 98,900 | 104,200 | +5.3% |
| **Avg CPU Utilization** | 69.1% | 36.8% | -46.7% |
| **p99 Latency** | 0.64ms | 0.46ms | -28.1% |

KeyDB’s ability to utilize 8 threads within a single process significantly reduces CPU saturation. The lower p99 latency is attributed to the elimination of network hops between cluster nodes and the reduction in context switching overhead inherent in managing multiple Redis processes.

---

### 4. Memory Overhead Breakdown
The memory efficiency of KeyDB is superior due to the consolidation of data structures:
*   **Per-Key Overhead:** KeyDB (46 bytes) vs. Redis (62 bytes). Redis Cluster incurs additional memory costs per key to track slot mapping and cluster-wide metadata.
*   **RSS Footprint:** KeyDB requires 418.5 MB vs. Redis Cluster’s 534.2 MB. 
*   **Fragmentation:** Because KeyDB runs as a single process, `jemalloc` manages a single heap, leading to more efficient memory allocation and reduced fragmentation compared to the fragmented heaps of six independent Redis processes.

---

### 5. Telemetry & Fault Recovery Audit
The telemetry data confirms that Redis Cluster is nearing its saturation point at 100k RPS, evidenced by higher CPU utilization (69.1%). KeyDB operates well within its headroom (36.8% CPU). 
*   **Fault Recovery:** While Redis Cluster provides native high availability via replicas, KeyDB supports active-active replication and multi-master setups. For a low-memory deployment, a single KeyDB instance with a standby replica is significantly more efficient than a 3-shard/3-replica Redis Cluster.

---

### 6. Production Deployment Blueprint
To achieve the target 100k RPS with minimal memory footprint, implement the following configuration:

*   **Instance Count:** 1 Primary KeyDB instance + 1 Read-Replica (for HA).
*   **Hardware Sizing:** 4 vCPU, 8GB RAM (High-frequency compute optimized).
*   **Core Allocation:** Pin KeyDB threads to physical cores to minimize cache misses.
*   **Configuration Tuning:**
    *   `server-threads 4`: Align with allocated vCPUs.
    *   `active-replica yes`: Enable for seamless failover.
    *   `maxmemory-policy allkeys-lru`: Ensure efficient eviction under memory pressure.
    *   `jemalloc` tuning: Ensure `background_threads` is enabled to assist in memory reclamation.

**Conclusion:** KeyDB provides a leaner, faster, and more manageable architecture for this specific throughput requirement.
