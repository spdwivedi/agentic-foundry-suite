# Infrastructure Evaluation Report: Redis Cluster vs. KeyDB
**To:** Engineering Leadership  
**From:** Principal Database Infrastructure Architect  
**Subject:** Architectural Evaluation for High-Throughput, Low-Memory Caching Layer

---

### 1. Executive Summary & Final Recommendation
For a workload requiring 100k read req/sec with a strict mandate for low-memory overhead, **KeyDB is the superior architectural choice.**

While Redis Cluster is the industry standard for horizontal scalability, its single-threaded shard model necessitates a multi-node deployment (6 instances in our test) to handle the 100k RPS threshold without saturating CPU. KeyDB’s multi-threaded, shared-nothing architecture achieves higher throughput (104.2k RPS) on a single instance with significantly lower memory footprint (418.5 MB vs 534.2 MB) and lower latency (0.46ms vs 0.64ms). 

**Recommendation:** Deploy KeyDB in a single-instance (or active-active pair) configuration. This reduces operational complexity, minimizes memory overhead by ~22%, and provides a more efficient CPU-to-throughput ratio.

---

### 2. Threading Model & Architectural Comparison
*   **Redis Cluster (Single-Threaded Shard Model):** Redis utilizes an event-loop architecture. To scale to 100k RPS, the workload must be partitioned across multiple shards. Each shard incurs the overhead of a full process, including its own memory management, background threads (AOF/RDB), and clustering metadata. This leads to "process sprawl."
*   **KeyDB (Multi-Threaded Shared-Nothing):** KeyDB extends the Redis codebase by implementing a multi-threaded architecture. It uses a shared-nothing approach where each thread handles its own event loop and data partition. This allows a single process to utilize multiple cores effectively, eliminating the need for complex clustering for a 100k RPS workload and drastically reducing the cumulative memory overhead of multiple process headers.

---

### 3. Throughput & Latency Analysis at 100k RPS
| Metric | Redis Cluster (6 nodes) | KeyDB (1 node) | Delta |
| :--- | :--- | :--- | :--- |
| **Measured QPS** | 98,900 | 104,200 | +5.3% |
| **CPU Utilization** | 69.1% | 36.8% | -46.7% |
| **p99 Latency** | 0.64ms | 0.46ms | -28.1% |

KeyDB demonstrates superior efficiency. The Redis Cluster approach requires 6 cores to maintain near-100k RPS, whereas KeyDB achieves higher throughput with 8 threads on a single instance at nearly half the CPU utilization. The lower p99 latency in KeyDB is attributed to reduced inter-node communication and the elimination of cluster bus overhead.

---

### 4. Memory Overhead Breakdown
The memory footprint difference is driven by two primary factors:
1.  **Process Overhead:** Redis Cluster requires 6 separate processes, each with its own `jemalloc` heap, stack space, and internal data structures. KeyDB consolidates this into one process.
2.  **Per-Key Metadata:** KeyDB’s optimized internal structures result in **46 bytes/key** compared to Redis’s **62 bytes/key**. In a high-cardinality cache (e.g., 10M keys), this represents a ~160MB savings in raw memory before accounting for fragmentation.
3.  **Clustering Metadata:** Redis Cluster maintains a hash slot map and node-to-node gossip protocol state, which consumes non-trivial memory as the cluster grows. KeyDB avoids this entirely in a single-instance deployment.

---

### 5. Telemetry & Fault Recovery Audit
*   **Telemetry:** Observations confirm that Redis Cluster is nearing its CPU ceiling at 100k RPS (69.1% utilization). Any spike in traffic would necessitate adding more shards, further increasing memory overhead.
*   **Fault Recovery:** Redis Cluster provides native sharding and automatic failover. KeyDB, when deployed as a single instance, lacks native sharding but supports Active-Active replication. For high availability, we recommend a two-node KeyDB setup using Active-Active replication, which still maintains a lower memory profile than a 6-node Redis Cluster.

---

### 6. Production Deployment Blueprint
To support 100k RPS with minimal memory overhead, implement the following:

*   **Instance Count:** 2 nodes (Active-Active configuration for HA).
*   **Hardware Sizing:** 4 vCPU, 8GB RAM per node (KeyDB is highly efficient; 8GB provides ample headroom for cache eviction policies).
*   **Configuration Tuning:**
    *   `server-threads 4`: Align with vCPU count.
    *   `active-replica yes`: Enable for high availability.
    *   `maxmemory-policy allkeys-lru`: Essential for cache stability.
    *   `jemalloc` optimization: Ensure `jemalloc` is compiled with the binary to manage fragmentation effectively.
*   **Network:** Ensure instances are placed in the same Availability Zone to maintain the observed sub-0.5ms p99 latency.
