# Infrastructure Evaluation Report: Redis Cluster vs. KeyDB

**To:** Engineering Leadership  
**From:** Principal Database Infrastructure Architect  
**Subject:** Architectural Evaluation for 100k RPS Caching Layer (Low-Memory Focus)

---

### 1. Executive Summary & Final Recommendation
For a deployment prioritizing **low-memory overhead** while sustaining 100k read req/sec, **KeyDB is the recommended solution.**

Redis Cluster, while industry-standard, forces a multi-process architecture to achieve high throughput on multi-core systems. This introduces significant memory bloat due to redundant process overhead, cluster bus metadata, and per-instance jemalloc fragmentation. KeyDB’s multi-threaded, single-instance architecture allows it to saturate modern CPU cores without the "sharding tax," resulting in a smaller memory footprint and reduced operational complexity.

---

### 2. Threading Model & Architectural Comparison
*   **Redis Cluster:** Operates on a single-threaded event loop per shard. To handle 100k RPS, one must deploy multiple shards (processes). Each process maintains its own memory heap, cluster bus connections, and internal data structures, leading to linear memory growth as the number of shards increases.
*   **KeyDB:** Utilizes a multi-threaded, shared-nothing architecture. It processes commands across multiple worker threads within a single process. This allows a single instance to utilize all available CPU cores, eliminating the need for cluster-level sharding for a 100k RPS workload.

---

### 3. Throughput & Latency Analysis at 100k RPS
Based on the latency math engine projections for an 8-core deployment:
*   **Redis Cluster:** Requires 4–6 shards to safely handle 100k RPS. Each shard operates at lower utilization, but the aggregate overhead of 4–6 processes increases the risk of context switching and cache misses.
*   **KeyDB:** A single instance can handle 100k RPS with ~50% core utilization on an 8-core machine. 
*   **Projected p99 Latency:** Both engines perform well, but KeyDB maintains lower tail latency under load due to the absence of inter-process communication (IPC) overhead and the elimination of cluster-wide gossip protocol traffic.

---

### 4. Memory Overhead Breakdown
| Metric | Redis Cluster (per shard) | KeyDB (single instance) |
| :--- | :--- | :--- |
| **Per-key Metadata** | 54–65 bytes | 42–50 bytes |
| **Process Overhead** | High (Multi-process) | Low (Single-process) |
| **Fragmentation** | High (Multiple jemalloc heaps) | Low (Unified heap) |
| **Cluster Metadata** | Significant (Hash slot maps) | Minimal (No sharding) |

KeyDB’s compact dictionary representation and unified memory management provide a **~20-30% reduction in baseline memory overhead** compared to a multi-shard Redis Cluster deployment.

### 6. Production Deployment Blueprint

**Recommended Configuration (KeyDB):**
*   **Instance Count:** 1 (Primary) + 1 (Replica for HA).
*   **Hardware Sizing:** 8 vCPU, 16GB RAM (assuming 100k RPS workload).
*   **Core Allocation:** Set `server-threads` to 8 to match vCPU count.
*   **Configuration Tuning:**
    *   `active-replica yes` (for seamless failover).
    *   `maxmemory-policy allkeys-lru` (to maintain low-memory footprint).
    *   `jemalloc` optimization: Ensure `MALLOC_CONF` is tuned for the specific Linux kernel to minimize fragmentation.
*   **Operational Note:** By avoiding Redis Cluster, you eliminate the complexity of hash-slot management and client-side redirection, significantly simplifying the application-side driver logic.
